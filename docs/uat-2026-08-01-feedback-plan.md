### กลุ่ม A — Legal & Payment Gateway (บล็อกการขายจริง)

#### F-01 · เอกสารกฎหมาย 4 ฉบับ เพื่อยื่นขอ payment gateway
- **ที่มา**: หน้า 2 (Next step), หน้า 12 ข้อ 1
- **ต้นฉบับ**: *"ทำ privacy notice, cookie policy, เงื่อนไขการใช้งาน, นโยบายคืนเงินและการขอลบบัญชี เพื่อทำ payment gateway"*
- **ประเภท**: ⚖️ Legal + 🔧 Function (ต้องมีหน้าเว็บจริง + ลิงก์ใน footer)
- **ยาก-ง่าย**: **M** (โครงหน้าเว็บ = S / เนื้อหากฎหมาย = ต้องมีคนตรวจ)
- **ความพร้อม**: 🟡
- **สถานะปัจจุบัน**: `apps/web` มี `privacy/page.tsx` (138 บรรทัด) และ `terms/page.tsx` (129 บรรทัด) อยู่แล้ว — **ขาด cookie policy และ refund/account-deletion policy**; `apps/proto` **ไม่มีสักหน้า**
- **ต้องเติมรายละเอียด**:
  1. ชื่อนิติบุคคล / เลขทะเบียนพาณิชย์ / ที่อยู่จดทะเบียน (payment gateway บังคับให้แสดง)
  2. เงื่อนไขคืนเงินจริง — คืนกี่วัน? คืนหลังเปิดรายงานแล้วได้ไหม? (สินค้าดิจิทัลเปิดแล้วปกติไม่คืน — ต้องเขียนให้ชัด)
  3. ระยะเก็บข้อมูล (retention) — ตอนนี้โค้ดมี `api/cron/purge-photos` แต่ยังไม่มี policy ของข้อมูลวันเกิด
  4. DPO / ช่องทางใช้สิทธิ PDPA (จะใช้ `info@minghe.work` ไหม)
  5. ใครเป็นคน sign-off เนื้อหา (ทนาย / เจ้าของธุรกิจ)
- **หมายเหตุ**: ข้อความกฎหมายผมร่างให้ได้ แต่ควรมีคนตรวจก่อนใช้จริง — ไม่ควร publish ร่างที่ AI เขียนโดยไม่มีคนตรวจ

### กลุ่ม B — Auth & User Flow

#### F-02 · ล็อกอินด้วยอีเมล + Google สำหรับบุคคลทั่วไป
- **ที่มา**: หน้า 3
- **ต้นฉบับ**: *"อยากให้ล็อกอินผ่านอีเมล คนทั่วไปและกูเกิล"*
- **ประเภท**: 🔧 Function
- **ยาก-ง่าย**: **M** (email/password มีแล้วใน `apps/web`) → **L** ถ้ารวม Google OAuth (ยังไม่มี — grep แล้วไม่เจอ oauth ในโปรเจกต์)
- **ความพร้อม**: 🟡
- **สถานะปัจจุบัน**: `apps/web/app/(auth)/login` + `api/auth/login|register|logout` มีแล้ว (custom, ไม่ใช่ NextAuth); `apps/proto` ไม่มี auth เลย
- **ต้องเติมรายละเอียด**:
  1. ใช้ NextAuth/Auth.js แทนของเดิม หรือแปะ Google OAuth เข้ากับระบบ auth เดิม?
  2. มี Google Cloud project / OAuth client ID แล้วหรือยัง? ใครถือ?
  3. ต้อง verify email (ส่งเมลยืนยัน) ไหม → ถ้าต้อง ต้องมีผู้ให้บริการอีเมล (Resend/SES)
  4. บัญชีเดียวกันใช้ได้ทั้งฝั่ง employer และ jobseeker หรือแยก?

#### F-03 · First-time trial — ให้เล่นโฟลว์ได้ก่อน แต่บังคับ login/สมัคร ตอนชำระเงิน
- **ที่มา**: หน้า 4
- **ต้นฉบับ**: *"First time trial: เข้าโฟลว์เช็คปกติ แต่เมื่อชำระเงินแล้ว ให้เค้าล็อกอินหรือสมัครใหม่"*
- **ประเภท**: 🔧 Function
- **ยาก-ง่าย**: **M**
- **ความพร้อม**: 🟡
- **ต้องเติมรายละเอียด**:
  1. บังคับ login **ก่อนจ่าย** หรือ **หลังจ่ายสำเร็จ** (สไลด์เขียนกำกวม — "เมื่อชำระเงินแล้ว ให้เค้าล็อกอินหรือสมัครใหม่")
     → แนะนำ: ให้ login/สมัคร **ก่อนกดจ่าย** เพราะถ้าจ่ายแล้วค่อยสมัคร มีโอกาสจ่ายเงินแล้วบัญชีหลุด ต้องมี recovery flow เพิ่ม
  2. ข้อมูลที่กรอกไว้ก่อน login ต้องถูก carry over หลัง login ใช่ไหม (ควรใช่)
  3. trial เล่นได้ถึงขั้นไหน — เห็นตัวอย่างรายงานบางส่วน (teaser) หรือแค่กรอกฟอร์มจบแล้วเจอ paywall?

#### F-05 · Login สำหรับ "บริษัท" เพื่อเก็บข้อมูล

### กลุ่ม C — Form UX (ชัดที่สุดในทั้ง PDF, ทำได้เร็ว)

#### F-07 · รูปแบบวันที่ต้องเป็น วัน/เดือน/ปี (DD/MM/YYYY) ทุกหน้า
- **ที่มา**: หน้า 10, หน้า 13 ข้อ 2, หน้า 15
- **ต้นฉบับ**: *"Month / Day / Year >> ปกติเป็น DMY"* · *"หน้าบริษัทนี้ระบุ เดือนวันปี ต้องปรับให้ใช้รูปแบบวันเดือนปี เหมือนกับหน้าบุคคล โดยมีตัวอย่างเช่น กรุณาระบุ วัน/เดือน/ปี เช่น 31/01/1990"*
- **ประเภท**: 🔧 Function + 🎨 Cosmetic
- **ยาก-ง่าย**: **S–M**
- **ความพร้อม**: 🟢
- **สาเหตุจริง**: โค้ดใช้ `<input type="date">` ([`components/forms.tsx:99`](apps/proto/components/forms.tsx#L99), [`employer/new/page.tsx:157`](apps/proto/app/employer/new/page.tsx#L157), [`jobseeker/new/page.tsx:129`](apps/proto/app/jobseeker/new/page.tsx#L129)) — **native date input จะแสดงลำดับตาม locale ของเบราว์เซอร์ ไม่ใช่ตามที่เรากำหนด** ถ้าเครื่องเป็น en-US ก็จะขึ้น MM/DD/YYYY เสมอ
- **ทางแก้ที่แนะนำ**: เปลี่ยนเป็น custom text input 3 ช่อง (DD / MM / YYYY) หรือ masked input + helper text `ตัวอย่าง: 31/01/1990` แล้วแปลงเป็น ISO ภายใน — จะได้ผลเหมือนกันทุกเครื่อง ทุก locale
- **ขอบเขต**: วันเกิดบุคคล, วันก่อตั้งบริษัท, ทุกที่ที่โชว์วันที่ในรายงาน — ควรทำ component กลางตัวเดียวใช้ทั้งโปรเจกต์

  3. ให้ preview พิกัด/ชื่อสถานที่ที่ parse ได้กลับไปให้ผู้ใช้ยืนยันไหม (แนะนำ: ควรมี — ลด error เงียบ)
